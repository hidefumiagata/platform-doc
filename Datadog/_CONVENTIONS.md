# Datadog ナレッジ 執筆規約

## 概要

本ナレッジは、ITコンサルタント・アーキテクト・エンジニアが読み、かつ AI が読み込んで質問に回答するための Markdown ドキュメント群である。全ファイルは本規約に従う。

## 1. 基準時点とバージョン

- Datadog は SaaS で継続的にリリースされ、名前付きリリースは存在しない。**基準は情報取得日（`last_verified`）**とする。本ナレッジの基準日は **2026-11-02**。
- Agent に関する記述は **Datadog Agent v7 系**を基準とし、機能の最低要件バージョンが判明していれば「（Agent 7.xx 以降）」と記載する。Agent v5/v6 は差分がある場合のみ言及する。
- プレビュー段階の機能は **`【Preview】`**、限定提供は **`【Limited Availability】`** を付ける（公式表記に従う）。一般提供（GA）は無表記。
- **改称・旧名称**：製品名が変更されている場合は「現名称（旧称：xxx）」と初出で併記し、`keywords` にも旧称を入れる（例：App and API Protection（旧称：Application Security Management / ASM）、Software Catalog（旧称：Service Catalog）、Cloud Security（旧称：Cloud Security Management / CSM）など）。改称時期が分かれば記載する。

## 2. Datadog サイト（リージョン）

- 基準サイトは **AP1（日本）**。ただし記述は全サイト共通を前提とし、サイトにより機能提供・エンドポイント・価格・データ保存場所が異なる場合は必ず明記する。
- サイト一覧と表記：`US1`、`US3`、`US5`、`EU1`、`AP1`、`AP2`、`US1-FED`（GovCloud）。
- サイト固有の差異は本文中に「> **サイト差異:** …」の形で記載する。

## 3. ファイル構成

```
Datadog/
  README.md            … 全体目次（AI が最初に読む入口）
  _CONVENTIONS.md      … 本規約
  glossary.md          … 用語集
  01_入門編/
  02_リファレンス/<領域>/
  03_導入編/
  04_応用編/
  assets/images/<ファイルのslug>/  … 画像
```

- 1ファイル1トピック。目安は 300〜1,500 行。
- ファイル名は英小文字のケバブケース（例：`log-management.md`）。

## 5. 本文の書き方

- 本文は日本語。製品用語・画面項目・メトリクス名・設定キー・API 名は**英語正式名称を主とし、初出時に日本語訳を併記**する（例：`Monitor（モニター）`）。
- 設定キー・メトリクス名・タグ・API エンドポイント・CLI コマンドはバッククォートで囲む（例：`DD_API_KEY`、`datadog.yaml`、`env:prod`、`system.cpu.user`）。
- 冒頭に「## 概要」、末尾に「## 参照元」を必ず置く。
- AI が単独のチャンクでも理解できるよう、各見出しの直下で主語を省略しない（「この機能は」ではなく「Log Management の Indexes は」）。
- 表を積極的に使う（設定項目、制限値、比較、料金）。
- アーキテクチャ・データフローは Mermaid 図で表現してよい。
- **リファレンスの各ファイルには「## 制限値・クォータ・デフォルト値」節を必ず置く**（保持期間、上限数、サイズ制限、レート制限、デフォルト値）。公開情報で見つからない項目は「公開情報では確認できず」と書く。
- **料金に関わる機能**は、リファレンスでも「## 課金への影響」節で課金単位を簡潔に書き、詳細は導入編の料金ファイルへリンクする。

## 6. 出典と情報の確度（全編必須）

- すべての事実記述は出典をたどれるようにする。節ごと、または文末に `[出典](URL)` を付け、末尾「## 参照元」に URL 一覧をまとめる。
- 情報源の優先順位：①Datadog 公式ドキュメント（docs.datadoghq.com）②公式サイト（datadoghq.com：料金ページ、製品ページ）・公式ブログ・リリースノート・Datadog Learning Center ③公式 GitHub（github.com/DataDog）④DASH 等の公式カンファレンス講演・事例 ⑤パートナー・第三者ブログ・技術ブログ（Zenn、Qiita、企業テックブログ）・調査会社 ⑥フォーラム投稿。
- 確度ラベル：公式情報以外に依拠する記述には以下を付ける。
  - `【第三者情報】` … パートナー・第三者の公開情報に基づく
  - `【推定】` … 複数情報からの推定、非公開価格・値引き率の推定値など
  - `【経験則】` … 一般に語られる実務上の知見
- Datadog は変化が速いため、**第三者情報は出典の公開日（または最終更新日）を併記**する（例：`[出典](URL)（2025-03 公開）`）。2年以上前の情報を使う場合は、現行仕様と食い違う可能性を注記する。
- 確認できなかった事項は推測で埋めず、「公開情報では確認できず」と書く。

## 7. 料金の扱い

- Datadog は定価を公式料金ページ（https://www.datadoghq.com/pricing/）で公開している。**公式掲載の定価は確度ラベル不要**だが、必ず「取得日（2026-11-02 時点）」と「契約形態（年契約 / 月契約 / オンデマンド）」を併記する。
- 料金は原則 USD で記載する。円建てに言及する場合は【推定】とし、換算レートと日付を明記する。
- 値引き率、Enterprise 契約条件、ボリュームディスカウント等の非公開情報は `【推定】` または `【第三者情報】` を付ける。
- 料金の数値はファイル間で矛盾させない。**料金の正本は `03_導入編/pricing-by-product.md`** とし、他ファイルで数値を引用する場合はこのファイルと一致させる。

## 8. 画像

- 画面スクリーンショット等の画像は、公式ドキュメント等から取得して `assets/images/<slug>/` に保存し、相対パスで参照する。公式ドキュメントの画像は概ね `https://datadog-docs.imgix.net/images/...` で配信されている。
- 画像の直下に必ず以下を書く（AI は画像を読めない前提で、文章だけで画面が分かるようにする）。
  - キャプション（何の画面か）
  - 画面の文章による説明（メニュー位置、主要項目）
  - 出典 URL と取得日
- 画像の著作権は Datadog, Inc. 等の権利者に帰属する。本リポジトリは社内の参照目的に限り、外部への再配布はしない。取得時に出典のライセンス表記を確認し、再利用が明示的に禁止されている場合は保存しない。
- 取得できなかった場合は無理に入れず、公式ページへのリンクと文章による画面説明で代替する。

## 9. 編ごとの役割

| 編 | 目的 | 読者 |
|---|---|---|
| 01_入門編 | Datadog を語るうえで必須の基本事項 | 入門者が最初に読む |
| 02_リファレンス | 製品仕様の詳細（機能、設定、制限値、API、画面） | AI 回答の主たる根拠、エンジニア・アーキテクト |
| 03_導入編 | 料金・エディション・契約、選定・比較、導入方法論、設計、運用、コンプライアンス | コンサルタント・PM・アーキテクト |
| 04_応用編 | 導入・運用経験者の知見（ベストプラクティス、失敗パターン、コスト最適化、事例） | 経験者・コンサルタント。**出典 URL 必須** |

## 10. ファイル間の整合

- 同じ事実（制限値、料金、製品名）を複数ファイルで書く場合は値を一致させる。迷ったらリファレンス（仕様）と `pricing-by-product.md`（料金）を正とする。
- 関連ファイルへは相対リンクで参照する（例：`[Log Management](../02_リファレンス/logs/log-management.md)`）。
